## Rust SDK

Use `satora-rust-sdk` for Rust integrations. The SDK handles swap creation, key management, and recovery. Its README lists supported swap routes and includes usage examples.

For a native Swift or Kotlin app, you can wrap the Rust SDK with your own bindings. Satora currently ships no Swift or Kotlin bindings.

## MCP for assistants and agents

Connect an MCP client to `https://api.satora.io/mcp` using Streamable HTTP.
The public, read-only endpoint offers token and route discovery, indicative
swap quotes, status lookup for a supplied swap UUID, and discovery of CCTP USDC
and LayerZero OFT USDT0 bridge capabilities. Bridge quotes and execution use
`@satora/swap`. No API key is required for MCP discovery.
Swap execution and wallet signing remain in your SDK or wallet integration.

## Iframe

Embed Satora Swaps directly into your application - no SDK integration required. Already used by [Arkade Wallet](https://arkade.money), [Alby Hub](https://albyhub.com), and more.

```html
<!-- Add your reflink from the Developer Portal to track swaps -->
<iframe
  src="https://app.satora.io?ref=YOUR_REFLINK"
  width="100%"
  height="700"
  frameborder="0"
  allow="clipboard-write"
/>
```

### Client compatibility headers

SDK requests include a client identifier and one protocol epoch header per protocol component:

```http
X-Lendaswap-Client: @satora/swap/0.5.0
x-satora-bitcoin-htlc-version: 1
x-satora-arkade-vhtlc-version: 1
x-satora-lightning-version: 1
x-satora-evm-erc20-htlc-version: 2
x-satora-evm-native-htlc-version: 2
```

`X-Lendaswap-Client` identifies the SDK and SDK version. EVM-target swap creation requires a recognizable `<sdk-name>/<semver>` value.

Each `x-satora-<component>-version` header carries the integer protocol epoch the client speaks for that component. Swap creation and the signing-sensitive per-swap endpoints check the components the swap uses and reject a client whose epoch for one of them is older than the server supports. Clients that still send the legacy `x-satora-server-version` header are accepted while every component is at epoch 1.

The EVM epoch also selects the contracts a new swap is created on. Epoch 2 gets HTLCErc20 v7 / HTLCCoordinator v5 / HTLCNative v2, where the depositor is the lock's sender (collaborative refund and rehash available). Epoch 1 and legacy clients keep getting the HTLCErc20 v6 / HTLCCoordinator v4 / HTLCNative v1 deployment while the server still serves it. Every later request about a swap follows the contracts and `evm_htlc_version` recorded on that swap.
